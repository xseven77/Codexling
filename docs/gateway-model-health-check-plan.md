# Gateway 模型健康巡检与目录动态过滤方案

## 背景与目标

网关导出的 `/v1/models` 目录在实际 Agent 调用时，部分模型由于上游账号未开通、格式不匹配、思考参数不兼容或上游瞬时过载而无法正常工作。
本方案实现了网关层面的**自动化健康巡检、严格可用性过滤、手动单账号重测、故障原因持久化记录与请求延时追踪**。

---

## 核心设计原则

1. **严格模式（Strict Mode）**：
   - `/v1/models` 接口仅导出经过验证判定为 `available` 的模型，以及由于网络波动/限流/服务过载被判定为 `error`（瞬时错误）的模型。
   - 确定不可用（`unavailable`，如 HTTP 404、模型不支持、无权限等）与尚未完成初次巡检的未检查（`unchecked`）模型一律从 `/v1/models` 中剔除。
   - 网关初次冷启动阶段（若没有任何历史巡检数据），提供短暂冷启动保护全量导出，待后台初次巡检完成后无缝转入严格过滤。

2. **全量保留与诊断视图（`/v1/models/all`）**：
   - 保留全部供应商与全部账号下的完整模型清单，并附带详细元数据：
     - `status`: `available`（可用）/ `unavailable`（不可用）/ `error`（瞬时异常）/ `skipped`（跳过）/ `unchecked`（未检查）
     - `reason`: 详细上游失败原因（包括 HTTP 状态码、错误关键词、finishReason 诊断片段）
     - `latencyMs`: 探测请求耗时毫秒数
     - `checkedAt`: 最近一次检查的时间戳
     - `retries`: 重试次数
     - `exported`: 是否被导出至 `/v1/models`

3. **探测方式与失败重试（Retry）**：
   - **请求形态**：向对应渠道与账号发送极简的 `"ping"` 请求。
     - Google Gemini (Cloud Code): 单轮 contents `[{role: "user", parts: [{text: "ping"}]}]`，不强制锁定 maxOutputTokens，防止思考预算耗尽导致空响应。
     - OpenAI / Codex: 原生 Responses 直连接口，发送标准 input message `"ping"` 并接收 SSE 校验。
     - OpenCode / DeepSeek: 标准 chat/completions 非流式单轮请求。
   - **防并发干扰与严格串行**：
     - 检查任务全局单例，同一时刻只允许一个检查任务运行（并发触发返回 HTTP 409 Conflict）。
     - 探测请求严格**逐条串行（Sequential）**执行，单条请求间隔 `1500ms`，避免高并发抢占正常业务额度或触发上游 429。
   - **试错重试机制**：
     - 遇到初次失败的模型，等待 `3000ms` 后进行第 2 次探测重试。
     - 若重试后恢复正常，判定为 `available`（标记 retries: 1）。
     - 若初次与重试均明确返回硬性不可用（如 404/不支持/格式拒绝），判定为 `unavailable`。
     - 若重试中存在超时/503/429 等波动，判定为 `error`（保留导出，记录具体波动原因）。
   - **IDE 专用补全模型**：
     - `tab_*` 前缀的 IDE 补全模型自动标记为 `skipped`，不发送探测请求。

4. **双触发机制（定时 + 手动）**：
   - **软件启动触发**：网关服务启动 15 秒后自动启动首轮全量巡检。
   - **每小时循环**：后台线程每隔 1 小时自动循环执行全量巡检，自动吸收新模型并清理失效模型。
   - **手动按账号触发**：Swift 端每个供应商的每个账号卡片均提供“检查可用性”按钮，支持独立定向重测。

## 接口设计

| 端点 | 方法 | 鉴权 | 说明 |
|---|---|---|---|
| `/v1/models` | GET | 公开 | Agent 消费的标准端点，已应用严格过滤，仅返回可用或瞬时异常模型 |
| `/v1/models/all` | GET | Bearer Token | 全量诊断端点，返回每账号详细模型健康记录、原因与耗时 |
| `/internal/model-check` | POST | Bearer Token | 触发巡检。Body 可选 `{ "provider": "google", "connectionId": "..." }`，不传默认全量 |
| `/internal/model-check/status` | GET | Bearer Token | 查询当前巡检任务进度与状态（`running`, `done`, `total`, `current`） |

---

## Swift 端 UI 交互

1. **“接入与模型”视图卡片**：
   - 账号信息栏新增健康统计徽章（例：`可用 21 · 不可用 2 · 异常 1`）。
   - 新增“检查可用性”按钮。巡检进行时自动显示 `ProgressView` 并在按钮中显示进度 `巡检 12/25`，同时全局禁用防止重复触发。
2. **全量模型抽屉（Drawer）**：
   - 展开可访问模型清单时，每行模型名称后方实时展示状态徽章与耗时（例：`🟢 可用 812ms` / `🔴 不可用` / `🟠 异常`）。
   - 鼠标悬停在徽章上即可查看上游记录的具体失败原因与错误诊断。
