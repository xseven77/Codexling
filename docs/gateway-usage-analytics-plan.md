# Gateway 用量分析与请求可观测性方案

## 1. 目标与结论

将现有的“当前进程快照 + 最近请求列表”升级为“可追溯的本地用量账本 + 实时请求视图”。用户可以按天、小时或自定义日期范围查询 Gateway 用量，并从 Agent、供应商、账号、模型和请求结果等维度定位消耗、延迟与异常。

本方案只记录经过 Codexling Gateway 的调用。它不混同以下两类信息：

- 本地 Agent 活动：用于展示 Codex、Hermes 等工作时长与任务数。
- 供应商账号额度：用于展示套餐、余额或订阅状态，不等于 Gateway 实际 Token 消耗。

现有 `recent_requests` 是有限条数的内存记录，重启后消失；Token 在部分路径上为估算值。因此它适合实时观察，但不能作为按天历史分析的事实来源。

## 2. 用户能够回答的问题

上线后，用户应能直接回答：

1. 今天、昨天或任意一段时间总共用了多少输入与输出 Token？
2. Token 主要由哪个 Agent、供应商、账号或模型消耗？
3. 某天的峰值发生在什么时段，是否伴随错误、工具调用或延迟升高？
4. 某次失败请求走到了哪个供应商/账号/模型，失败原因是什么？
5. 统计数字是上游实际返回、供应商报告，还是本地估算？

## 3. 数据口径

### 3.1 一条请求账本事件

每次 Gateway 请求结束时写入一条事件。流式请求在收到最终 usage 或流结束时落账；网络错误也需落一条失败事件。

| 分类 | 字段 |
| --- | --- |
| 时间 | 请求开始、结束、完成耗时、本地时区下的日期与小时 |
| 来源 | Agent、入口协议、请求类型、是否流式 |
| 路由 | 供应商、账号、模型别名、目标模型、路由 ID |
| Token | 输入、输出、缓存读取、缓存写入、总量 |
| 性能 | TTFT、总耗时、请求/响应字节数（可选） |
| 结果 | HTTP 状态、成功/失败、标准化错误类别、重试次数 |
| 工具 | 请求中工具数、模型返回 tool call 数 |
| 费用 | 成本、币种、费用来源（如可获得） |
| 可信度 | `actual`、`provider_reported`、`estimated`、`unavailable` |

### 3.2 Token 与成本规则

- 优先使用上游最终响应中的 `usage`。例如 OpenAI、Anthropic、Gemini 或兼容接口有明确 usage 时，标记为“实际用量”。
- 上游没有 usage 时，沿用本地估算，但必须标记为“估算”；汇总图和详情都不能把它伪装成精确值。
- 流式响应只记录最终块中的 usage；若没有最终块，记录估算值或 `unavailable`。
- 缓存读写 Token 仅在上游提供时展示，不反推、不臆造。
- API Key 的可计费模型可按可维护的价格表估算成本；OAuth、会员或订阅账号默认显示“订阅/额度用量，不计费”，不能展示虚假的人民币成本。
- 失败前未取得 usage 时，Token 为空而非零；失败请求数仍计入成功率与错误分布。

### 3.3 时区与粒度

- 账本时间统一以 UTC 毫秒保存，查询时以用户选择的时区聚合；默认系统本地时区。
- 范围不超过 48 小时时按小时展示；3–90 天按日展示；更长范围按周或月展示。
- “今天”以查询时区的自然日为准。夏令时当天允许出现 23 或 25 个小时，不强行补齐错误的 24 小时。

## 4. 存储与服务设计

### 4.1 本地账本

使用 Gateway 管理的 SQLite 数据库，建议路径：

```text
~/Library/Application Support/Codexling/gateway-telemetry.sqlite
```

数据库使用 WAL 模式；请求完成后经轻量写入队列批量提交，不能让统计写入阻塞模型响应。

建议保留策略：

- 请求原始元数据：90 天。
- 小时/日聚合：至少 24 个月。
- 设置页提供 30 天、90 天、1 年、永久四档，以及“清除所有用量数据”。

不写入 prompt、响应正文、API Key、OAuth token 或完整 Authorization header。账号在本地可使用稳定内部 ID 关联；界面按用户配置的账号名显示。

### 4.2 表与聚合

| 表 | 作用 |
| --- | --- |
| `request_events` | 请求级明细，支持追查单次调用与错误 |
| `usage_hourly` | 小时粒度聚合，用于今日与短周期趋势 |
| `usage_daily` | 日粒度聚合，用于长期趋势与快速加载 |
| `telemetry_settings` | 时区、保留策略、收集开始时间等本地设置 |

聚合维度至少包含：日期/小时、Agent、供应商、账号、模型、入口协议、状态类别与 Token 可信度。高基数的请求 ID 不进入聚合表。

### 4.3 Gateway 查询接口

保留现有 `/status` 作为低成本实时快照；新增分析接口，避免 Dashboard 直接读数据库：

```text
GET /telemetry/summary?from&to&timezone&filters
GET /telemetry/timeseries?metric=tokens&interval=hour|day|week&from&to&filters
GET /telemetry/breakdown?dimension=agent|provider|account|model|status&from&to&filters
GET /telemetry/requests?from&to&cursor&sort&filters
```

所有接口返回收集开始时间、时区与 Token 可信度汇总。例如“82% 实际用量、18% 估算”，避免用户误读统计精度。

## 5. 界面信息架构

不增加主侧栏入口。将现有“监控概览”扩展为三个页签：

```text
监控概览
├── 概览
├── 使用分析
└── 请求明细
```

现有“实时请求”保留为快捷入口，默认显示实时流；切换日期范围时与“请求明细”使用同一套查询与筛选能力。

### 5.1 概览页

顶部统一放置：`今天｜昨天｜近 7 天｜近 30 天｜自定义日期`、时区说明和“与上一周期对比”开关。

首屏六张指标卡：

- 总 Token：输入/输出拆分，并显示实际与估算占比。
- 请求量与成功率。
- 估算成本；订阅/OAuth 账号显示额度用量说明。
- P50 / P95 TTFT。
- 缓存命中率。
- Tool Calls。

下方展示：Token 趋势、请求/错误趋势、延迟趋势、Top 供应商/账号/模型，以及高耗时或失败请求快捷入口。工作时长卡继续属于本地 Agent 活动区，不与 Token 图叠加。

### 5.2 使用分析页

主图为输入/输出 Token 堆叠柱状图，提供 `Token｜请求数｜成本｜延迟` 指标切换。悬停一根柱时显示：

- 时间桶范围。
- 输入、输出、缓存 Token 和总 Token。
- 实际/估算比例。
- 请求数、成功率、P50/P95 延迟。

图表下方为可切换排行：

| 切换维度 | 每行显示 |
| --- | --- |
| Agent | Token、请求数、成功率、TTFT |
| 供应商 | Token、成本、失败率 |
| 账号 | Token、可用模型数、失败率 |
| 模型 | 输入/输出 Token、请求数、平均耗时 |

默认展示前 10 项，其余归入“其他”；点击某项会将其作为全页筛选条件。

### 5.3 请求明细页

列表支持日期范围、Agent、供应商、账号、模型、状态、协议和 Token 可信度筛选，以及按时间、Token、TTFT、总耗时排序。

建议列：时间、Agent、供应商 · 账号 · 模型、输入/输出 Token、TTFT、总耗时、状态。点击行打开详情抽屉，显示完整路由、Token 来源、工具调用、缓存、错误类别和请求 ID；默认不显示用户输入或模型输出。

## 6. 交互与状态规则

- 无数据：显示所选日期范围内无 Gateway 请求，并说明数据从启用账本之日开始收集。
- 部分估算：指标卡和图例出现“含估算”提示；详情可精确区分单条请求的来源。
- 失败请求：红色状态仅代表请求失败，不把 Token 空值显示为 `0`。
- 筛选联动：概览页点击模型/账号/错误状态后，跳转到请求明细并保留日期与筛选条件。
- 刷新：实时数据 10–30 秒刷新；历史聚合在切换范围、筛选或手动刷新时查询，避免频繁扫描数据库。
- 导出：第二阶段提供导出当前筛选结果为 CSV；导出同样不含 prompt、响应正文或认证信息。

## 7. 分期落地

### 第一阶段：可信账本与按天可见

1. 写入持久化 `request_events`，覆盖成功、失败与流式结束。
2. 为 Token 增加实际/估算来源标记，并解析上游 usage。
3. 增加小时/日聚合与日期范围查询 API。
4. 完成概览的日期选择器、Token 主图、核心指标卡和请求明细筛选。

### 第二阶段：成本与深度定位

1. 缓存 Token、价格表与 API 模型成本估算。
2. Agent/供应商/账号/模型分解排行与图表联动。
3. 请求详情抽屉、错误分类、CSV 导出、保留策略设置。

### 第三阶段：主动管理

1. 日/周 Token 预算与阈值提醒。
2. 某供应商、账号或模型错误率/延迟异常提醒。
3. 可选的本地报告导出与长期趋势对比。

## 8. 验收标准

- Gateway 重启后，已记录的日期数据仍可查询。
- 选择任意自然日，可看到该日输入、输出、总 Token 与请求数；其值等于筛选后的明细汇总。
- 在短时间范围按小时、长时间范围按日/周正确聚合，且时区切换结果正确。
- 每个 Token 数值都可区分实际、供应商报告、估算或不可用。
- 用户可从任一图表下钻到对应的供应商、账号、模型与请求详情。
- 原始账本与导出内容不包含 prompt、响应正文、API Key 或 OAuth token。
- 聚合查询不影响正在进行的模型请求，实时页仍可稳定刷新。

## 9. 非目标

- 不将供应商网页中显示的订阅余额伪装为可精确换算的 Token 成本。
- 不对未经过 Gateway 的本地 Agent 调用做推测性统计。
- 不在默认状态下采集或展示用户提示词、模型回复或工具参数。
- 不承诺在功能启用前回填历史请求；界面需明确显示数据收集起始日。
